## How the system works today (observed in source)

- **Build** (`engine/engine.js` `Engine.build`, L147): compiles IR, computes per-node digests (`digests`, L58: hash of type, params, input digests, file digests for `source.files`, `def.digest`, `def.src`). For each build node in topological order: memo hit → reuse; stored hit (`env.artifacts.has(storeKey)`) → `Lazy` memo entry; else delta (`tryDelta`) or full (`def.map` / `def.all`). Saves via `store.save` and records lineage via `store.lineageRecord`. Results live in `this.memo` keyed by digest — engine-global, not per snapshot.
- **"Current artifacts"** (`Engine.artifacts`, L556): recomputed from current digests (which read `env.files()` each time). Returns null if any digest is missing (i.e. sources changed). Builds `art = {key, byId, chunks, order, indexes, synonyms, docs, links}` and caches the last one in `this._art`. There is no published-snapshot object; "current" is whatever memo matches today's files.
- **Chunk union**: every `chunks`-typed build node is merged into one `art.chunks`. Arrays go into a Map (later `Map.set` wins), record views (stored outputs) are kept aside and combined via `unionChunks` (`engine/records.js` L30) where the Map is consulted *before* any view regardless of graph order. So the winning record for a duplicated ID depends on whether a node was cold (array) or stored (view). This confirms finding #2a by mechanism.
- **Reading order** (`artifacts` L608): taken from the first non-`enrich` chunk node ("primary"), an implicit rule.
- **Record view** (`natives/persist.go` `recordsViewJS`, L437): JS class with `__records`, `get/has/size/length/order/values/toArray/toJSON`. `isView`/`asArray` in `records.js` distinguish it; `buildCtx.firstOf` and `inputArrays` call `asArray`, but `resolveBakes` (L517) passes `outputs.get(...)` unconverted — a view in Go hosts, an array otherwise (finding #2b). Bake cache key `key0 = hash([docs.map(id + sections.length), chunks.length])` — counts only; a view's `length` exists but a records2 docs view is not an array so `docs.map` would throw for stored docs. (Deduction: stored docs + a bake can fail outright, not only mis-key; not verified by running.)
- **Query** (`engine/session.js` `Session.run`, L37): gets `art`, or awaits `engine.buildShared` then re-reads `art`. Runs live nodes, each through `ctx` closures over `art` (`chunk`, `docChunks`, `neighbors`, `index`, …). `decorateResult` (L361) attaches `chunk/top/explain/toJSON` reading `art.chunks` — the result retains live handles indefinitely.
- **Served app** (`runner/serve.go` `serveHarness`): `__serve.run` awaits `session.run`, then calls `collect()` (which may `eng.gc`), then `art()` again to pack chunk bodies + neighbors. If a refresh published newer outputs during the await, packing reads the newer generation (or `art()` is null → crash on `a.chunks`). `__serve.refresh` calls `eng.build` directly (not `buildShared`), then `collect()`. `__serve.chunk/doc` read `art()` at request time by bare ID.
- **GC of handles** (`Engine.gc`, L410): memo entries whose digest is not live are pushed onto `retired`; the *next* gc closes them (`__records.close()` / `__ix.close()`). Two refreshes during one awaiting query close what the query holds (finding #3a). `tryDelta.loadBase` also pushes opened bases into `retired`.
- **Native opening paths** (`persist.go` `load`, L198): records/records2/bleve loads call `addCloser(r.Close)` (runtime-close hook); `addCloser` falls back to a no-op when `env.AddCloser` is nil (L47–50; same in `bm25_native.go` L124). Delta outputs are opened in `natives/delta.go` (`OpenRecords2`, L101) via `markdown_native.go` `parseDelta/chunkDelta` → `records2Object` → `ctx.store.view` with no `addCloser` (finding #3c). Engine gc and the runtime closer can both close the same reader; `Records2.Close` (records2.go L650) is idempotent-ish (sets closed, closes shards). Shards open lazily (`shard`, L509) — a reader can need files later.
- **Store** (`artifacts/store.go`): layout `<dir>/<ns>/<key[:2]>/<key>.{json,bin,<codec>}`; `Has` validates payload presence/size. `writeAtomic` = temp+rename, no fsync. `List` (L272) `SkipDir`s any directory whose name contains `.` — including the walk root itself, so a root like `~/.cache/x.store` lists nothing (finding #2c).
- **Lineage** (`artifacts/lineage.go`): `LineageKeep=32`, `LineageSearch=8`. `LineageRecord` truncates to 32 entries; `GC(keep)` only deletes entries still listed → versions evicted past 32 are never collected (finding #3b). `GC` also deletes `.tmp-*` dirs older than one hour without knowing whether a live build owns them. No namespace lock exists anywhere (grep of runner: none).
- **Shared builds** (`Engine.buildShared`, L695): keyed by joined digests; the second caller receives the first caller's promise, whose `opts.signal` and `onEvent` belong to the first request (finding #4b).
- **Async bridges**: `ragjs/sample.go` `newSample` and `ragjs/decide.go` `newDecide` classify the outcome inside the goroutine *before* `defer cancel()` runs, then post. `natives/rerank.go` `rerankAsync` (L145–170) checks `callCtx.Err()` *inside the posted settle callback*, after the goroutine's deferred `cancel()` already ran, so every provider error is reported as `cancelled` (finding #5). None of the three remove their abort listener. All three duplicate: lifetime ctx, abort listener, goroutine, post settle.
- **SSE** (`server/sse.go`): `streamSink.Emit` cancels the request if the 256-entry queue stays full 100 ms. `sseWriter.write/ping` ignore flush errors; `pump` ignores write errors (L154, L182, L186). No write deadlines. If the client stops reading and TCP buffers fill, `Fprintf` blocks; handlers wait `<-pumped`/`<-done` forever. In `handleVerb` the inflight slot is released by `defer a.release()` only after that — slot held indefinitely (finding #4a). `handleRun` takes no inflight slot at all. Orchestration (sink, pump goroutine, close, join, terminal event) is duplicated between `rag.go` `handleRun` and `verbs.go` `handleVerb`.
- **Model fallback** (`llm/gepp/backend.go` `preferred`, L114): when `EnabledModels` is empty and the default is unavailable, the loop over `EnabledModels` does nothing → no model, though "empty" means "all enabled" in `enabled()` (finding #6). Fix needs a deterministic order (eligible is a map).
- **Graph** (`graph/graph.js`): `finalize` (L405) discovers references four ways: `n.in` data inputs, `def.uses(p)` artifact refs derived from params (e.g. `p.index:'text'` → `ix-text`, builtins.js L180), `when` decision refs via `whenRefs` (declarative `decision:'node.q'` string or regex over lambda source), and lambda signal reads. `applyOp 'rename'` (L877) rewrites only `in` and `outputs`, not `when.decision`, lambda text, or params backing `uses` (finding #7b; also index rename). `remove` checks `uses` users but not `when` dependents. `export/html.js` removes all submit-triggered live non-answer nodes, then answer/context, via `applyOps`; a remaining node whose `when` reads a removed classifier fails `finalize` (finding #7a). Export embeds `engine.files()` only.
- **Browser shell** (`web/app-shell/shell.js` L29–46): caches chunks, neighbors, docs and *missing* keys by bare ID for the page lifetime; no generation.
- **Scope** (`engine/scope.ts`): strict TS; `newScope`, `scoped` capture signal/detail/onEvent synchronously. A good base for typed operation contracts.
- **Tooling** (`pkg/ragjs/src/README.md`, `package.json`): `pnpm build`, `pnpm check` (tsc + Biome + generated-bytes + `scripts/runtime.test.mjs`), Go tests `go test ./pkg/ragjs ./pkg/runner ./web`.

## Unresolved / underspecified decisions found

1. Snapshot granularity: per plan build key, per corpus, or per app? Today memo is engine-global; a verb may run a different plan sharing a corpus. Proposal: per normalized build-graph identity, with registry sharing for common artifacts.
2. Whether queries ever wait for a refresh: original says background refresh must not block; but today a query that sees changed files triggers a build itself. Need an explicit rule ("query never triggers rebuild if a published snapshot exists; refresh owner does").
3. Who triggers refresh — watcher only, or also queries? Affects staleness. Proposal: watcher/manual/post-sync only.
4. Duplicate-ID adoption policy in the registry (reuse vs reject).
5. Fusion across differently enriched datasets: default rule (reject vs require canonical projection).
6. Result materialization budget size and error code.
7. Retention policy for old snapshots (count; privacy).
8. Stale-generation lookup: keep N retired generations resolvable, or always answer stale.
9. Deletion behavior for decision dependents (reject by default?).
10. Partial/deferred LLM outputs (`engine.partial`) — how they map to snapshots (published-but-incomplete?). Original does not mention them. Needs a decision.
11. `docs` identity across sources: original proposes source identity + vault path; current IDs derive from path slugs (`core/identity.ts`). Changes chunk IDs → affects evals/fixtures.
12. fsync requirement level and supported platforms.
13. Write-deadline value and heartbeat byte limits.
14. Whether direct `/run` gets admission control (it currently has none).

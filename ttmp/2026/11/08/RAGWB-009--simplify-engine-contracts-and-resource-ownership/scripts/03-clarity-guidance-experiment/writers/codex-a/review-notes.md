## Comprehension gaps

1. Section 2, “computes build digests, reuses memoized values”: a newcomer can infer the flow but still needs the purpose of a digest. Add a definition at first use: key describing the producing step and its inputs, so matching output can be reused. Also define provider and reranking in the orientation rather than letting their names carry the explanation. Code clarifies these roles in Engine.digests and reports.js.
2. Section 3's P/E example and later snapshot discussion: the guide gives the pieces separately but never shows the actual relationship of a snapshot ID, an index binding and a hit. Add a compact record example with snapshot A containing document dataset D, chunk datasets P/E, enriched index binding E, a returned ref and a later GUI lookup. Show that B may have E2 while A's ref still means E. Source explains today's absent provenance; this is target design, not observed JSON.
3. Section 4, “slot identifies the plan's build structure”: the refinement is useful but its freshness policy is implicit. Clarify slot eligibility is unchanged structure/configuration, and serving old data during background refresh is an explicit target policy. Prevent an old build finishing late from overwriting a newer generation. The original does not specify concurrent publication ordering; choose a simple one-active-job-per-slot publication coordinator with coalesced follow-up refresh, label as proposed refinement, and include a regression. Existing engine builds can overlap across version digests, so code does not supply this target rule.
4. Section 6, “one operation arbiter”: explain its concrete role and timing rather than naming it. Add short Go-like lifecycle pseudocode showing cancellation and worker result competing through the same synchronized terminal-state method; settlement captures the fixed outcome before cleanup. Clarify ignored late results still release worker-owned resources. Source rerank callback establishes why this matters; source does not implement the proposal.
5. Section 6, “returning an admission slot must respect ... actual remaining work”: this leaves the intern with no actionable initial contract. State the bounded-join deadline is an implementation gate; transport and producer cleanup both must terminate for slot recovery acceptance. If a provider ignores cancellation, retain worker/resource accounting and report timeout rather than closing live handles or claiming completion. Do not invent an unbounded retry path. This remains a real policy/capability decision.
6. Section 7 “named dependency bindings”: add a tiny conceptual component configuration that maps a stable callback binding `route` to graph node `classifier`. Explain rename affects that mapping, with no proposed public builder spelling asserted. Existing lambda scanning is insufficient; a code search does not resolve the API choice.
7. Section 8 table abbreviates “engine/...” and some Go files without saying the root. Establish that JavaScript module references are relative to pkg/ragjs/src; Go paths are repository-relative. Add module.go and web/app-shell/shell.js to affected boundaries so a newcomer knows where host loading and remote data reach the GUI.
8. Section 11 lists choices without alternatives/status, despite writing guidance requesting compact consequential decisions. Replace its opening inventory with a small decision record table: synchronous vs async collections, provenance vs union, leased snapshots vs rebuild delay, detached results vs user release, exclusive namespace vs cross-process leases. Separate target requirements inherited from 009 from writer-proposed implementation refinements.

## Technical corrections and contract precision

9. Section 3 sketch has nonnullable ChunkDataset.document(chunkId) despite Dataset.get allowing missing IDs. Make document return null for missing chunk and order return an empty sequence for a valid source document with no chunks; reject a reference from a different source dataset. Label omitted Chunk/SearchOptions definitions as omissions. Record immutability is runtime-enforced, not implied by readonly T[]. Code cannot decide the new API; this correction prevents contradictory missing-record behavior.
10. Section 4 duplicate adoption paragraph says “Reject duplicate adoption of the identical live handle” while failure sketch closes r. An erroneous re-adoption could close a handle the registry already owns. Restrict opener/adoption API to newly opened owned handles; choose explicit duplicate-ID rejection with caller close, while registry reuse is acquire/retain of the existing entry without reopening. Mark that as proposed policy. Snapshot sharing then uses retain, not adoption. Omit claims that malformed trusted native code cannot violate ownership. Code has no central registry yet.
11. Section 4 ownership sketch discards close failure. Show cleanup errors recorded alongside adoption failure or label omitted reporting explicitly; each close attempt is accounted for and errors surface. Also distinguish snapshot current/retained root, query lease and builder scope; release snapshot entry references only when all interests in that snapshot end.
12. Section 6 SSE setup needs order: validate deadline capability before committing headers; one writer owns start/body/heartbeats/terminal. A terminal response must be sent through this writer rather than a handler writing after pump join. Preserve bounded initial setup and explain unsupported wrappers fail setup. Existing handlers violate single ownership today; target should not leave this implicit.
13. Section 9 plan phases 3/4 imply persistent publication could be shipped safely before durable inventory/lock. Add explicit integration checkpoint: runtime snapshot phase can be tested in memory/private fixture stores, but safe persistent serving/online GC is enabled only with the store phase. No compatibility mode is introduced; this is a rollout gate.
14. Section 10 bake row conflates dataset immutability and cache identity but no row explicitly calls for deterministic iteration/null/materialization/unknown-reference behavior. Add a conformance paragraph and reference the inspected full/delta and refresh suites by file/symbol. Include no-current-snapshot build, failed refresh preserving last-good snapshot and late-build ordering tests.
15. Current “same JavaScript runtime runs in browsers” could imply identical index scores. Add that shared collection/ownership semantics do not require identical backend rankings, while preserving existing parity/quality comparisons.
